# 04. 기술 아키텍처

## 한눈에

```

│  입력 · 카메라 · UI · 사운드 · 렌더링(MultiMesh 벨트, 구역 셰이더)         │

        상태/이벤트                              요청(명령)
┌───────────────┴──────────────────────────────────▼───────────────────────┐
│  Net 계층: 요청 RPC, 이벤트 방송, 스냅샷. 전송은 ENet 또는 Steam           │
└───────────────▲──────────────────────────────────┬───────────────────────┘
```

지금은 `SimWorld` 한 파일(약 1,000줄)에 공장·전력·격자·소지품·밭이 함께 있다. 복원이 들어오는 M3에서 주제별 파일로 나눈다.

### 계층 규칙

1. `sim/`은 `RefCounted`와 기본형만 쓴다. `get_tree()`, 오토로드, `Node` 참조가 있으면 리뷰에서 거절한다. 이 규칙 덕분에 헤드리스 테스트, 다른 언어로의 이식, 결정론이 가능하다.
2. `game/`의 View는 상태를 **읽고** 요청을 **보낼** 뿐이다. 상태를 직접 바꾸지 않는다.
3. 상태 변경은 전부 `World`의 명령 함수를 지난다. 호스트 자신의 입력도 같은 길을 간다.

## 네트워크

### 무엇을 어떻게 동기화하나

| 대상 | 권한 | 방법 | 빈도 |
| --- | --- | --- | --- |
| 플레이어 이동 | **본인 클라이언트** | 비신뢰 RPC로 호스트에 보고 → 호스트가 걸러서 중계, 받는 쪽에서 보간 | 20Hz |
| 플레이어 사격·명중 | 사수 클라이언트가 판정 → 호스트 검증 | RPC | 사건마다 |
| 체력, 쓰러짐 | 호스트 | 변화 시 신뢰성 이벤트 + 4Hz 갱신(회복 표시용) | |
| 전리품, 소지품 | 호스트 | 당사자에게만 신뢰성 이벤트 | 사건마다 |
| 적 | 호스트 | 호스트가 전체 목록(위치, 방향, 체력, 공격 준비 여부)을 방송, 클라이언트는 꼭두각시를 보간 | 10Hz |
| 투사체 | 호스트 | 생성·종료만 신뢰성 이벤트로, 중간 궤적은 각자 계산 | 사건마다 |
| 구조물 설치·철거 | 호스트 | 요청 RPC → 검증 → 이벤트 방송 | 사건마다 |
| 공장 상태 | 호스트 | 클라이언트가 같은 시뮬레이션을 호스트의 틱을 따라 실행 + 해시 비교 | 틱 번호 10Hz, 해시 10초마다 |
| 구역 진행도, 레시피 해금 | 호스트 | RPC 이벤트 | 변할 때 |

### 왜 이동은 클라이언트 권한인가

친구끼리 하는 협동 PvE다. 서버 권한 이동은 클라이언트 예측과 보정을 직접 구현해야 하고(Godot에 내장 기능이 없다) 조작감을 해칠 위험이 크다. 얻는 것은 부정행위 방지인데 이 게임에서는 가치가 낮다.

호스트는 최소한의 검사만 한다: 순간이동 수준의 속도 초과, 맵 밖 좌표. 위반 시 마지막 유효 위치로 되돌린다.

명중 판정도 같다. 사수 화면에서 맞았으면 맞은 것이다(쏘는 손맛이 지연에 영향받지 않는다). 호스트는 `대상이 살아 있나 / 사거리 안인가 / 연사 속도가 무기 수치 이내인가 / 탄약이 있나`만 확인한다. PvP 아레나도 같은 방식을 쓴다. 친구끼리의 미니게임에 그 이상은 필요 없다.

### 사격 검증 (구현됨)

쏘는 쪽 화면에서 맞았으면 "이 적을 이 무기로 맞혔다"를 호스트에 보고한다. 피해량은 보내지 않는다. 호스트가 다음을 확인하고 직접 계산한다.

| 확인 | 거절 사유 |
| --- | --- |
| 그 무기가 존재하는가 | `unknown_weapon` |
| 한 번의 보고에 든 탄환 수가 무기의 탄환 수 이하인가 | `too_many_pellets` |
| 직전 보고와의 간격이 연사 간격의 60% 이상인가 | `too_fast` |
| 쏜 사람이 살아 있는가 | `not_alive` |
| 대상이 살아 있고 150m 안인가 | (그 탄환만 무시) |

피해 = 무기 피해 × 거리 감소(호스트가 아는 위치 기준) × 머리 배율. 규칙은 `CombatRules`에 있고 단위 테스트가 있다. 탄약 수는 아직 호스트가 세지 않는다(인벤토리가 생기는 M2에서 추가).

### 요청과 이벤트 (구현됨)

상태를 바꾸는 모든 일은 **(작업 이름, 인자 배열)** 한 쌍이다. RPC는 요청용 하나(`_req`)와 이벤트용 하나(`_ev`)뿐이다.

```
클라이언트                          호스트                              모든 피어
   │ _req("place", [def, cell, rot])   │                                    │
   ├──────────────────────────────────▶│ _do(): 형식·권한·자리·받침·재료·거리 │
   │                                   │ 통과 → 이벤트 인자 확정(ID, 주인)    │
   │                                   │ _apply() ── _ev(틱, "place", […]) ─▶│ _apply()
   │◀────── (거절) 이유 ───────────────┤                                    │
```

- 호스트의 `_do()`만 검증한다. `_apply()`는 검증 없이 상태만 바꾸며 호스트와 클라이언트가 **같은 함수**를 쓴다. 그래서 새 작업을 추가할 때 양쪽 구현이 어긋날 수 없다.
- **호스트는 클라이언트가 보낸 어떤 값도 믿지 않는다.** 인자는 개수와 형을 먼저 확인하고, 보낸 사람은 인자가 아니라 연결에서 확인한다.
- 설비를 쓰는 작업(넣기, 꺼내기, 레시피, 밭)은 그 구조물에서 10m 안에 있어야 하고, 손 제작은 작업대에서 10m 안이어야 한다.
- 예측 설치는 하지 않는다. 미리보기는 클라이언트가 같은 규칙으로 계산해 보여 줄 뿐이다.

| 작업 | 하는 일 |
| --- | --- |
| `place` `belt` `free` | 설치(칸 / 벨트 경로 / 자유 배치). 비용 차감 |
| `remove` | 철거. 비용과 내용물을 철거한 사람에게 |
| `insert` `take` | 소지품 ↔ 구조물 |
| `recipe` | 제작 기계의 레시피 변경(안에 든 것은 돌려받는다) |
| `craft` `research` | 작업대 손 제작, 연구(월드 공유) |
| `plant` `water` `harvest` | 밭 |
| `consume` | 탄약 사용(재장전할 때) |
| `gather` | 광맥·결정 덩어리를 손으로 캔다(5m 안, 자리마다 대기 시간) |
| `join` `grant` `boss` | 호스트 내부용: 플레이어 등록(시작 지급품), 전리품 지급, 우두머리 처치 기록과 코어 지급 |

### 공장 상태 복제 (구현됨)

구조물 수천 개의 상태를 일일이 보내지 않는다. 시뮬레이션이 결정론적이라는 점을 이용해 **입력만 보낸다.**

1. 호스트는 틱을 돌릴 때마다 틱 번호를 보낸다. 클라이언트는 같은 `sim/` 코드를 그 번호까지 돌린다.
2. 호스트는 상태를 바꾸는 모든 일(설치, 철거, 손으로 넣기)을 "**몇 틱에** 무엇을 했다"로 방송한다. 클라이언트는 그 틱까지 먼저 진행한 뒤 같은 일을 적용한다.
3. 틱 번호와 이벤트는 같은 신뢰성·순서 보장 채널로 가므로, 클라이언트의 상태는 호스트와 비트 단위로 같아진다. 보정으로 물건이 튀는 일 자체가 없다.
4. 호스트는 100틱(10초)마다 상태 해시를 보낸다. 다르면 클라이언트가 스냅샷을 다시 받는다. 정상이라면 일어나지 않아야 하며, 일어나면 결정론이 깨진 버그다.

대역폭은 월드 크기와 무관하게 틱당 수 바이트다. 대가는 **클라이언트도 호스트만큼 CPU를 쓴다**는 것이고, 이것이 틱 코어를 네이티브로 옮기는(D-025) 또 하나의 이유다. 출시 규모에서 약한 PC가 따라오지 못하면 먼 청크를 생략하는 방식을 다시 검토한다(Q-15).

Godot의 `MultiplayerSpawner`/`MultiplayerSynchronizer`는 쓰지 않는다. 필요한 것이 "순서가 보장된 이벤트"와 "몇 개의 위치 값"뿐이어서 직접 만든 RPC가 더 단순하고, 화면 없이 여러 프로세스로 자동 점검하기 쉽다(D-037).

### 중도 참가 (구현됨)

1. 연결 → 클라이언트가 게임 버전(네 자리)과 콘텐츠 해시, 이름을 보낸다. 다르거나 정원(8명)이 찼으면 사유와 함께 거절한다.
2. 호스트가 월드 스냅샷(세이브와 같은 직렬화)을 압축해 60KB 조각으로 보낸다.
3. 그 뒤의 이벤트는 같은 채널로 스냅샷 **다음에** 도착하므로 따로 쌓아 둘 필요가 없다.
4. 클라이언트가 스냅샷을 적용하면 월드에 들어간다.

세이브와 스냅샷이 같은 코드를 쓰므로 저장 왕복 테스트가 중도 참가도 함께 검증한다.

### 자동 통합 점검

`tools/net_test.sh`가 화면 없이 프로세스 4개(호스트, 처음부터 참가, 늦게 참가, 방문자 역할)를 띄운다. 호스트가 공장을 짓고 일부를 철거하고, 클라이언트도 설치를 요청한다. 250틱에 네 프로세스의 상태 해시가 모두 같아야 하고, 방문자의 설치는 거절돼야 하며, 재동기화가 한 번도 없어야 통과다. CI가 푸시마다 돌린다.

### 전송 추상화

`Net.host(mode)`, `Net.join(target)`만 전송 종류를 안다. 그 뒤로는 `multiplayer.multiplayer_peer`에 넣을 뿐이므로 게임 코드는 ENet인지 Steam인지 모른다.

- 개발: ENet + 로컬호스트. 한 PC에서 창 2~4개를 띄워 테스트한다(에디터의 다중 인스턴스 실행 기능). 8인 부하는 입력을 자동으로 넣는 헤드리스 클라이언트로 채운다.
- 최대 접속 수는 8(호스트 포함)로 전송 계층에서 제한한다.
- Steam: 로비 생성 → 친구 초대 → 로비 소유자의 Steam ID로 접속. Steam 중계를 쓰므로 포트 개방이 필요 없다.

## 시뮬레이션

### 틱 순서

`SimWorld.tick()`은 호스트에서 물리 프레임에 누적 시간을 재서 0.1초마다 한 번 호출한다. 한 틱 안의 순서는 고정이다.

1. 전력망: 수요·공급 집계 → 충족률
2. 발전기: 연료 소모
3. 채굴기·제작 기계: 진행 → 출력 버퍼
4. 출력 포트 → 벨트 라인 투입
5. 벨트 라인 전진 (하류에서 상류 순서)
6. 벨트 라인 끝 → 입력 포트 / 분배기 / 저장소
7. 밭 성장
8. 비콘: 캡슐 소모 → 구역 진행도
9. 통계 누적(최근 60초 생산량)

순회 순서는 항상 구조물 ID 오름차순 또는 미리 계산한 위상 순서다. Dictionary 순회 순서나 부동소수점에 결과가 의존하면 안 된다.

### 결정론

완전한 록스텝은 아니다(호스트가 권한을 갖고 스냅샷으로 보정한다). 그래도 결정론을 지키는 이유는 세 가지다.

- 클라이언트가 호스트와 같은 상태를 스스로 계산할 수 있어, 입력만 보내면 된다(위 "공장 상태 복제").
- 테스트가 "N틱 뒤 상자에 정확히 M개"를 단언할 수 있다.
- 버그를 세이브 파일 + 틱 수로 재현할 수 있다.

### 토폴로지 캐시

설치·철거가 일어날 때만 다시 계산한다: 벨트 라인 병합, 포트 연결 그래프, 전력망 구성, 위상 순서. 틱에서는 캐시된 배열만 순회한다.

## 렌더링

| 대상 | 방법 |
| --- | --- |
| 벨트 위 물건 | 아이템 종류별 `MultiMeshInstance3D`. 슬롯 위치 + 틱 사이 보간으로 인스턴스 변환을 갱신 |
| 벨트 자체 | 구간 메시 + UV 스크롤 셰이더 |
| 건물 조각 | 같은 메시는 청크 단위 MultiMesh로 묶는 것을 M2에서 측정 후 결정 |
| 먼 설비 | 가시 범위 밖은 애니메이션·파티클·소리 정지, 벨트 물건 숨김 |
| 구역 복원 | 전역 셰이더 파라미터(구역 진행도)를 지면·식생·안개가 읽는다 |

## 성능 예산

기준 사양: **GTX 1660급 GPU, 6코어 CPU, 1080p**. 8인 접속, 호스트 기준.

| 항목 | 예산 |
| --- | --- |
| 프레임 | 60fps (16.6ms) |
| 공장 시뮬레이션 | 틱당 평균 2ms 이하, 최악 5ms |
| 슬라이스 목표 규모 | 설비 500개, 벨트 2,000칸 |
| 출시 목표 규모 | 설비 5,000개, 벨트 20,000칸 |
| 동시에 활동하는 적 | 40 (8인이 두 구역에 나뉘어 싸우는 경우 기준) |
| 클라이언트 업로드 | 20KB/s 이하 |
| 호스트 업로드 | 클라이언트당 50KB/s 이하 (7명 접속 시 합계 350KB/s ≈ 2.8Mbps) |
| 자동 저장 | 프레임 끊김 5ms 이하(파일 쓰기는 스레드) |
| 중도 참가 | 출시 목표 규모에서 15초 이내 |

**M0에서 측정했다.** GDScript는 슬라이스 규모에서 평균 0.61ms(통과), 출시 목표 규모에서 10.8ms(5배 초과)다. 단계별로는 제작 준비 2.2 / 전력 0.7 / 제작 진행 2.5 / 벨트 3.6 / 출력 2.2ms로 한 곳에 몰려 있지 않다. 한두 군데를 고쳐서 5배를 줄일 수 있는 모양이 아니어서 틱 코어를 네이티브로 옮기기로 했다([D-025](07_decisions.md)). 측정은 `godot --headless -s tools/bench_factory.gd`로 다시 할 수 있다.

8인이 되면서 늘어나는 비용은 주로 플레이어 동기화(7명 × 30Hz)와 공장 스냅샷을 받는 사람 수다. 공장 시뮬레이션 자체는 인원과 무관하다.

## 테스트와 자동화

| 종류 | 대상 | 시점 |
| --- | --- | --- |
| 단위(헤드리스) | `sim/` 전체: "채굴기 1 + 분배기 + 제련기 2가 정상 상태에 든 뒤 600틱 동안 저장소에 주괴가 정확히 60개 늘어난다" | 커밋마다 |
| 데이터 검증 | 레지스트리 로딩, 참조 무결성 | 커밋마다 |
| 저장 왕복 | 저장 → 불러오기 → 상태 동일 | 커밋마다 |
| 마이그레이션 | `fixtures/`의 옛 세이브 불러오기 | 커밋마다 |
| 벤치마크 | 대규모 가짜 공장의 틱 시간 | 마일스톤마다, 회귀 시 실패 처리 |
| 멀티 수동 | 2~4창 체크리스트(설치, 참가, 이탈, 호스트 종료) | 마일스톤마다 |

CI(`.github/workflows/build.yml`)는 푸시마다 단위 테스트, 슬라이스 규모 벤치마크, Windows 내보내기, 내보낸 팩의 자동 점검을 돌리고 테스트 빌드를 올린다. 자세한 것은 [08](08_dev_process.md).

## 코드 규칙

- 정적 타입 필수. 프로젝트 설정에서 타입 없는 선언을 경고가 아닌 오류로 올린다.
- 파일·폴더는 `snake_case`, 클래스는 `PascalCase`, 시그널은 과거형(`structure_placed`).
- 씬 하나에 스크립트 책임 하나. 다른 씬의 내부 노드 경로를 직접 참조하지 않는다.
- 호스트 전용 코드는 함수 첫 줄에서 `multiplayer.is_server()`를 확인한다.
- 매직 넘버는 데이터(`.tres`)로. 코드에 수치를 적지 않는다.

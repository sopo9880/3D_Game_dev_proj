# 04. 기술 아키텍처

## 한눈에

```
┌──────────────────────── 클라이언트(모든 플레이어) ────────────────────────┐
│  입력 · 카메라 · UI · 사운드 · 렌더링(MultiMesh 벨트, 구역 셰이더)         │
│  View 계층: 상태를 읽어 그린다. 게임 규칙을 결정하지 않는다                │
└───────────────▲──────────────────────────────────┬───────────────────────┘
        상태/이벤트                              요청(명령)
┌───────────────┴──────────────────────────────────▼───────────────────────┐
│  Net 계층: 요청 RPC, 이벤트 방송, 스냅샷. 전송은 ENet 또는 Steam           │
└───────────────▲──────────────────────────────────┬───────────────────────┘
┌───────────────┴────────────── 호스트만 ──────────▼───────────────────────┐
│  Game 계층: 요청 검증 → 상태 변경 → 이벤트 발행                           │
│  Sim 계층(순수 로직): 공장 · 전력 · 농사 · 복원     AI · 전투 판정         │
│  Save 계층: 버전 관리 · 원자적 쓰기 · 백업                                │
└──────────────────────────────────────────────────────────────────────────┘
```

호스트는 클라이언트이기도 하다(리슨 서버). 싱글 플레이는 접속자 0명인 호스트다. **싱글 전용 코드 경로는 만들지 않는다.**

## 기술 선택

| 항목 | 선택 | 비고 |
| --- | --- | --- |
| 언어 | GDScript (정적 타입 필수) | 시뮬레이션 코어가 예산을 넘으면 그 부분만 C#/GDExtension으로 옮긴다 |
| 렌더러 | Forward+ | |
| 물리 | Jolt (Godot 내장) | 프로젝트 생성 시 엔진 버전의 지원 여부 확인 |
| 멀티 | Godot 고수준 멀티플레이 API(`MultiplayerAPI`, RPC) | |
| 전송 | 개발: `ENetMultiplayerPeer` / 출시: GodotSteam의 Steam용 MultiplayerPeer | 전송 교체가 게임 코드에 보이지 않게 한다 |
| Steam | GodotSteam | 로비, 초대, 업적. 개발 중 테스트 앱 ID 480 사용 |
| 테스트 | GUT 또는 gdUnit4 | M0에서 하나를 고른다 |
| 지형 | 슬라이스는 직접 만든 메시. 이후 Terrain3D 검토 | |

외부 애드온의 버전과 호환성은 도입 시점에 공식 문서로 다시 확인한다. 이 문서의 이름은 후보를 가리킬 뿐 버전을 보증하지 않는다.

```

├─ core/                   # 오토로드
│   ├─ registry.gd         # 콘텐츠 정의 로딩·검증
│   ├─ session.gd          # 호스트/참가/종료, 플레이어 목록, 역할
│   ├─ net.gd              # 전송 생성(ENet/Steam), 연결 이벤트
│   ├─ world.gd            # WorldState 소유, 명령 진입점, 이벤트 버스
│   └─ save.gd             # 저장/불러오기/마이그레이션
├─ data/                   # .tres: items/ recipes/ structures/ weapons/ enemies/ crops/ zones/
├─ sim/                    # ★ 순수 로직. Node, 씬 트리, 싱글턴 접근 금지

│   ├─ power/              # power_grid.gd
│   ├─ farming/            # plot.gd
│   ├─ restoration/        # zone.gd, beacon.gd
│   ├─ grid/               # 칸 점유, 청크, 포트 연결 그래프
│   └─ sim_world.gd        # tick() 한 번에 전체를 한 걸음 진행
├─ game/                   # 씬과 Node 스크립트
│   ├─ player/             # 이동, 카메라, 상호작용, 인벤토리 UI 연결
│   ├─ weapons/
│   ├─ enemies/            # AI 상태 기계, 스포너
│   ├─ build/              # 건축 모드, 미리보기, 구조물 View
│   ├─ factory_view/       # 벨트 MultiMesh, 기계 애니메이션·상태 아이콘
│   ├─ world/              # 맵 씬, 구역 볼륨, 복원 연출
│   └─ ui/
├─ net/                    # 복제: commands.gd, events.gd, snapshot.gd
├─ save/migrations/
└─ tests/
    ├─ sim/                # 헤드리스 단위 테스트
    ├─ save/               # 마이그레이션, 왕복(저장→불러오기→비교)
    └─ fixtures/           # 버전별 샘플 세이브
```

### 계층 규칙

1. `sim/`은 `RefCounted`와 기본형만 쓴다. `get_tree()`, 오토로드, `Node` 참조가 있으면 리뷰에서 거절한다. 이 규칙 덕분에 헤드리스 테스트, 다른 언어로의 이식, 결정론이 가능하다.
2. `game/`의 View는 상태를 **읽고** 요청을 **보낼** 뿐이다. 상태를 직접 바꾸지 않는다.
3. 상태 변경은 전부 `World`의 명령 함수를 지난다. 호스트 자신의 입력도 같은 길을 간다.

## 네트워크

### 무엇을 어떻게 동기화하나

| 대상 | 권한 | 방법 | 빈도 |
| --- | --- | --- | --- |
| 플레이어 이동 | **본인 클라이언트** | `MultiplayerSynchronizer`, 다른 사람 쪽에서 보간 | 20~30Hz |
| 플레이어 사격·명중 | 사수 클라이언트가 판정 → 호스트 검증 | RPC | 사건마다 |
| 체력, 사망, 전리품 | 호스트 | RPC 이벤트 | 사건마다 |
| 적 | 호스트 | `MultiplayerSpawner` + `MultiplayerSynchronizer`, 클라이언트 보간 | 10~15Hz |
| 구조물 설치·철거 | 호스트 | 요청 RPC → 검증 → 이벤트 방송 | 사건마다 |
| 공장 상태 | 호스트 | 청크별 스냅샷 + 클라이언트 시각 예측 | 가까운 청크 2Hz |
| 구역 진행도, 레시피 해금 | 호스트 | RPC 이벤트 | 변할 때 |

### 왜 이동은 클라이언트 권한인가

친구끼리 하는 협동 PvE다. 서버 권한 이동은 클라이언트 예측과 보정을 직접 구현해야 하고(Godot에 내장 기능이 없다) 조작감을 해칠 위험이 크다. 얻는 것은 부정행위 방지인데 이 게임에서는 가치가 낮다.

호스트는 최소한의 검사만 한다: 순간이동 수준의 속도 초과, 맵 밖 좌표. 위반 시 마지막 유효 위치로 되돌린다.

명중 판정도 같다. 사수 화면에서 맞았으면 맞은 것이다(쏘는 손맛이 지연에 영향받지 않는다). 호스트는 `대상이 살아 있나 / 사거리 안인가 / 연사 속도가 무기 수치 이내인가 / 탄약이 있나`만 확인한다. PvP 아레나도 같은 방식을 쓴다. 친구끼리의 미니게임에 그 이상은 필요 없다.

### 명령과 이벤트

```
클라이언트                         호스트                         모든 피어
   │  request_place(def, cell, rot)  │                               │
   ├────────────────────────────────▶│ 권한·점유·재료 검사            │
   │                                 │ 상태 변경, ID 발급             │
   │                                 ├──── ev_structure_placed ─────▶│
   │◀──── (실패 시) ev_rejected ─────┤                               │
```

- 요청 RPC: `any_peer`, `reliable`. 이름은 `request_*`.
- 이벤트 RPC: `authority`, `reliable`. 이름은 `ev_*`.
- **호스트는 클라이언트가 보낸 어떤 값도 믿지 않는다.** 보낸 사람은 인자가 아니라 `multiplayer.get_remote_sender_id()`로 확인한다.
- 클라이언트는 설치 요청 후 응답을 기다리는 동안 반투명 "대기" 모형을 보여 준다. 예측 설치는 하지 않는다.

### 공장 상태 복제

구조물 수천 개를 `MultiplayerSynchronizer`로 동기화하지 않는다.

1. **토폴로지**(무엇이 어디에 있고 어떻게 연결되나)는 설치/철거 이벤트로 모든 클라이언트가 똑같이 갖는다.
2. **동적 상태**(벨트 슬롯, 기계 버퍼와 진행도)는 클라이언트가 **같은 `sim/` 코드를 로컬에서 돌려** 그린다. 표시용일 뿐 권한은 없다.
3. 호스트는 플레이어 근처 청크의 실제 상태를 2Hz로 압축해 보낸다. 클라이언트는 받은 값으로 덮어쓴다.
4. 먼 청크는 보내지 않는다. 다가가면 스냅샷이 오고 그때부터 맞춰진다.
5. 플레이어가 설비 패널을 열고 있는 동안에는 그 설비 상태를 더 자주(10Hz) 받는다.

이 방식이 M0 프로토타입에서 잘 안 맞으면(보정 때 물건이 눈에 띄게 튄다) 대안은 "클라이언트는 시뮬레이션하지 않고 스냅샷 사이를 보간만 한다"이다. 어느 쪽이든 `sim/`과 View가 분리돼 있으면 바꿀 수 있다.

### 중도 참가

1. 연결 → 호스트가 게임 버전과 콘텐츠 해시를 확인한다. 다르면 거절한다.
2. 호스트가 틱 경계에서 월드 스냅샷(세이브와 같은 직렬화)을 만들어 압축 전송한다. 큰 데이터는 조각내어 보낸다.
3. 전송 중 발생한 이벤트는 호스트가 그 클라이언트용으로 쌓아 뒀다가 스냅샷 뒤에 보낸다.
4. 클라이언트가 적용을 마치면 `ready`를 보내고 플레이어가 스폰된다.

세이브와 스냅샷이 같은 코드를 쓰므로 저장 왕복 테스트가 중도 참가도 함께 검증한다.

### 전송 추상화

`Net.host(mode)`, `Net.join(target)`만 전송 종류를 안다. 그 뒤로는 `multiplayer.multiplayer_peer`에 넣을 뿐이므로 게임 코드는 ENet인지 Steam인지 모른다.

- 개발: ENet + 로컬호스트. 한 PC에서 창 2~4개를 띄워 테스트한다(에디터의 다중 인스턴스 실행 기능).
- Steam: 로비 생성 → 친구 초대 → 로비 소유자의 Steam ID로 접속. Steam 중계를 쓰므로 포트 개방이 필요 없다.

## 시뮬레이션

### 틱 순서

`SimWorld.tick()`은 호스트에서 물리 프레임에 누적 시간을 재서 0.1초마다 한 번 호출한다. 한 틱 안의 순서는 고정이다.

1. 전력망: 수요·공급 집계 → 충족률
2. 발전기: 연료 소모
3. 채굴기·제작 기계: 진행 → 출력 버퍼
4. 출력 포트 → 벨트 라인 투입
5. 벨트 라인 전진 (하류에서 상류 순서)
6. 벨트 라인 끝 → 입력 포트 / 분배기 / 저장소
7. 밭 성장
8. 비콘: 캡슐 소모 → 구역 진행도
9. 통계 누적(최근 60초 생산량)

순회 순서는 항상 구조물 ID 오름차순 또는 미리 계산한 위상 순서다. Dictionary 순회 순서나 부동소수점에 결과가 의존하면 안 된다.

### 결정론

완전한 록스텝은 아니다(호스트가 권한을 갖고 스냅샷으로 보정한다). 그래도 결정론을 지키는 이유는 세 가지다.

- 클라이언트 시각 예측이 호스트와 거의 같아져 보정이 눈에 띄지 않는다.
- 테스트가 "N틱 뒤 상자에 정확히 M개"를 단언할 수 있다.
- 버그를 세이브 파일 + 틱 수로 재현할 수 있다.

### 토폴로지 캐시

설치·철거가 일어날 때만 다시 계산한다: 벨트 라인 병합, 포트 연결 그래프, 전력망 구성, 위상 순서. 틱에서는 캐시된 배열만 순회한다.

| 대상 | 방법 |
| --- | --- |
| 벨트 위 물건 | 아이템 종류별 `MultiMeshInstance3D`. 슬롯 위치 + 틱 사이 보간으로 인스턴스 변환을 갱신 |

| 구역 복원 | 전역 셰이더 파라미터(구역 진행도)를 지면·식생·안개가 읽는다 |

## 성능 예산

기준 사양: **GTX 1660급 GPU, 6코어 CPU, 1080p**. 4인 협동, 호스트 기준.

| 항목 | 예산 |
| --- | --- |
| 프레임 | 60fps (16.6ms) |
| 공장 시뮬레이션 | 틱당 평균 2ms 이하, 최악 5ms |
| 슬라이스 목표 규모 | 설비 500개, 벨트 2,000칸 |
| 출시 목표 규모 | 설비 5,000개, 벨트 20,000칸 |
| 동시에 활동하는 적 | 30 |
| 클라이언트 업로드 | 20KB/s 이하 |
| 호스트 업로드 | 클라이언트당 50KB/s 이하 |
| 자동 저장 | 프레임 끊김 5ms 이하(파일 쓰기는 스레드) |
| 중도 참가 | 출시 목표 규모에서 15초 이내 |

**M0에서 출시 목표 규모를 가짜 데이터로 채워 틱 시간을 잰다.** GDScript로 예산을 못 맞추면 그 시점에 코어 언어를 결정한다. 나중으로 미루지 않는다.

## 테스트와 자동화

| 종류 | 대상 | 시점 |
| --- | --- | --- |
| 단위(헤드리스) | `sim/` 전체: "채굴기 1 + 분배기 + 제련기 2가 정상 상태에 든 뒤 600틱 동안 저장소에 주괴가 정확히 60개 늘어난다" | 커밋마다 |
| 데이터 검증 | 레지스트리 로딩, 참조 무결성 | 커밋마다 |

| 마이그레이션 | `fixtures/`의 옛 세이브 불러오기 | 커밋마다 |
| 벤치마크 | 대규모 가짜 공장의 틱 시간 | 마일스톤마다, 회귀 시 실패 처리 |
| 멀티 수동 | 2~4창 체크리스트(설치, 참가, 이탈, 호스트 종료) | 마일스톤마다 |

CI는 GitHub Actions에서 헤드리스 Godot으로 위의 "커밋마다" 항목을 돌린다. M0에서 구성한다.

## 코드 규칙

- 정적 타입 필수. 프로젝트 설정에서 타입 없는 선언을 경고가 아닌 오류로 올린다.
- 파일·폴더는 `snake_case`, 클래스는 `PascalCase`, 시그널은 과거형(`structure_placed`).
- 씬 하나에 스크립트 책임 하나. 다른 씬의 내부 노드 경로를 직접 참조하지 않는다.
- 호스트 전용 코드는 함수 첫 줄에서 `multiplayer.is_server()`를 확인한다.
- 매직 넘버는 데이터(`.tres`)로. 코드에 수치를 적지 않는다.

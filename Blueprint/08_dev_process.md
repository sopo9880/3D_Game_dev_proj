# 08. 개발 절차

## 버전

형식은 `MAJOR.MINOR.PATCH.BUILD`. 예: `0.1.0.37`.

| 자리 | 올리는 때 | 누가 |
| --- | --- | --- |
| MAJOR | 정식 출시(1), 세이브가 호환되지 않는 큰 개편 | 사람이 결정 |
| MINOR | 새 기능 묶음. 출시 전에는 마일스톤 하나가 끝날 때마다 | 커밋으로 |
| PATCH | 기능 추가 없이 버그 수정·수치 조정만 한 배포 | 커밋으로 |
| BUILD | 빌드할 때마다 | CI가 자동으로 (GitHub Actions 실행 번호) |

- 기준값은 `project.godot`의 `application/config/version`. 저장소에는 BUILD를 항상 `0`으로 둔다(`0.1.0.0`). CI가 빌드할 때 실제 번호로 바꿔 넣는다.
- 게임 화면 오른쪽 위에 버전이 표시된다. 버그나 의견을 전달할 때 이 번호를 함께 적는다.
- 출시 전 MINOR와 마일스톤의 대응: `0.1` = M0, `0.2` = M1, `0.3` = M2, `0.4` = M3(버티컬 슬라이스), `0.5` = M4, 그 뒤는 기능 묶음마다.
- 멀티플레이 접속은 **네 자리 전부와 콘텐츠 해시**가 같을 때만 허용한다. 친구끼리 같은 빌드를 받아 쓰는 게임이므로 엄격하게 잡고, 버전이 다르면 어느 쪽이 낮은지 알려 준다.
- 세이브 포맷 버전(`save_version`)은 이것과 별개의 정수다([03](03_data_model.md#버전-관리)).
- 정식 배포는 `v0.2.0` 같은 태그를 푸시하면 CI가 릴리스를 만든다.

## 브랜치와 CI

- 푸시할 때마다 `.github/workflows/build.yml`이 다음을 순서대로 한다.
  1. 프로젝트 가져오기(import)
  2. 단위 테스트 (`tests/`)
  3. 슬라이스 규모 공장 벤치마크 — 평균 틱 4ms 초과 시 실패(공용 CI 장비가 느린 것을 감안해 예산 2ms의 두 배)
  4. 멀티플레이 통합 점검 (`tools/net_test.sh`: 호스트 1 + 클라이언트 3)
  5. 내보낸 팩으로 사격장 자동 점검(이동, 사격, 재장전, 연사 속도, 올라타기, 아레나 규칙)
- **Windows 빌드는 푸시마다 만들지 않는다.** `v0.2.0` 같은 태그를 푸시하거나 Actions에서 수동 실행(Run workflow)할 때만 만들어 올린다.
- Godot 실행 파일과 내보내기 템플릿은 공식 릴리스에서 받고 SHA-512로 확인한다.

## 직접 실행

Godot 4.7.2(표준판)로 프로젝트 폴더를 열고 F5. 명령줄에서는:

```bash
godot --headless --import
```

```bash
godot --headless -s tests/run_tests.gd
```

```bash
godot --headless -s tools/bench_factory.gd
```

```bash
godot --headless -- --selftest
```

```bash
tools/net_test.sh
```

멀티플레이를 직접 해 보려면 게임을 두 번 실행해 한쪽에서 "호스트", 다른 쪽에서 "참가"를 누른다(같은 PC면 주소 `127.0.0.1`, 포트 24565/UDP). 명령줄로는 `godot -- --host`, `godot -- --join=127.0.0.1`, 혼자는 `godot -- --single`.

벤치마크는 `-- --units=87`처럼 기준 라인 개수를 줄 수 있다(기본 870 = 출시 목표 규모).

## 테스트 빌드

조작감처럼 사람이 해 봐야 아는 것은 내려받아 실행하는 Windows 빌드로 확인한다.

**받는 곳**

- `v*` 태그를 푸시하면 저장소의 **Releases**에 그 버전이 올라간다.
- 태그 없이 받고 싶으면 **Actions → ci → Run workflow**로 수동 실행한 뒤 그 실행의 **Artifacts**에서 받는다.
- `dev-latest`는 푸시마다 갱신하던 예전 방식의 마지막 빌드(v0.1.1)다. 더는 갱신되지 않는다.

zip을 풀고 `Edenfall.exe`를 실행한다. 설치는 없다. 서명되지 않은 빌드라 Windows가 경고를 띄우면 "추가 정보 → 실행"을 누른다.

**사격장에 들어 있는 것** (시작 화면에서 "사격장")

- **F2로 규칙 전환**: `협동 (PvE)` ↔ `전술 아레나 (PvP)`. 아레나 규칙은 달리기·슬라이딩이 없고, 멈춰서 쏘면 첫 발이 정확하고, 움직이며 쏘면 크게 퍼지고, 소총 머리 한 발에 쓰러진다. 두 규칙의 수치는 따로 조정하고 따로 내보낸다(JSON의 `profile` 항목으로 구분).
- 무기 3종(권총, 돌격소총, 샷건), 고정 표적 10/20/35/50m, 움직이는 표적 2개, DPS 허수아비
- 표적 도전(T): 무작위로 나오는 표적 15개를 쓰러뜨리는 시간과 명중률
- 이동 연습 구역: 높이별 상자, 경사로, 슬라이딩으로 지나가는 낮은 문
- 화면 왼쪽 위: FPS, 속도, 명중률 등 통계

그래픽과 소리는 전부 임시(상자 모델, 코드로 합성한 소리)다.

**의견 주는 법**

1. `F1`로 수치 조정 패널을 연다. 현재 든 무기와 이동 관련 수치가 슬라이더로 나온다.
2. 값을 바꾸면 즉시 적용된다. 패널을 닫고 쏴 보고, 다시 열어 고치기를 반복한다.
3. 마음에 드는 상태에서 **"JSON 복사 + 파일 저장"**을 누른다. 세 무기와 이동 수치 전체가 클립보드에 복사된다.
4. 그 JSON과 함께 느낀 점을 말로 적어 전달한다("소총 반동이 너무 약하다", "슬라이딩이 짧다" 등).

전달받은 JSON의 `weapons` 배열은 `data/weapons.json`과 같은 형식이라 그대로 반영할 수 있다.

**첫 빌드에서 특히 확인하고 싶은 것**

1. 쏘는 순간의 반응이 즉각적인가(소리, 반동, 적중 표시)
2. 반동을 손으로 제어할 수 있는가. 밋밋하거나 과하지 않은가
3. 이동과 슬라이딩이 답답하지 않은가
4. 무기 3종의 성격이 다르게 느껴지는가
5. 마우스 감도 기본값이 적당한가(`[` `]`로 조절)
6. 전술 아레나 규칙(F2)에서: 멈추고 쏘는 리듬이 생기는가, 소총 반동 패턴을 몇 번 쏴 보면 익힐 수 있는가, 이동 속도가 답답하지 않은가
